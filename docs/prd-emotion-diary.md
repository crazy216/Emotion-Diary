# PRD：情绪日记（Emotion Diary）

## 1. 需求背景

现代人日常积累了大量的生活照片，但照片背后的情绪与故事往往没有被记录和梳理，随着时间流逝逐渐被遗忘。用户需要一个能够"看到照片、听你讲述、替你落笔"的情感陪伴型产品：用户上传一张有故事的照片，AI 识别画面内容并像朋友一样与用户聊聊照片背后的事，再用柔和的笔法把这段情绪凝练成一篇日记，保存下来供日后查阅，并可随时再与 AI 就此展开新的对话。

本需求为情绪日记产品的第一版（MVP），目标是跑通"上传照片 → AI 识图对话 → 生成日记 → 保存查阅 → 二次对话"的完整业务闭环，验证情感陪伴式日记的核心体验。

经与用户确认，首版关键技术决策如下：产品形态为 Web 网页应用，前端采用 React，后端采用 FastAPI；接入第三方多模态大模型 API（具体模型选型暂不限定），大模型应用开发框架采用 LangGraph；需要登录注册体系，登录方式支持"邮箱 + 验证码"与"邮箱 + 密码"；数据不做纯本地存储，而是通过 Docker 部署 MinIO 存储图片、MySQL 存储其余业务数据。

## 2. 目标与价值

**目标：**
- 跑通从照片上传到日记生成、保存、查阅、二次对话的完整闭环
- 支持用户注册登录，实现个人日记数据的隔离与持久化
- 图片统一存入 MinIO 对象存储，日记、对话、用户等结构化数据存入 MySQL
- AI 能够准确识别照片内容，并以情感陪伴的姿态与用户自然对话
- AI 生成的日记笔法柔和、贴合用户讲述的情绪，单版本生成且支持重新生成

**价值：**
- 对用户：把"沉默的照片"转化为可回味、可被理解的情绪记录，获得被陪伴感
- 对产品：以低门槛（拍照/上传即可）的情绪记录切入，沉淀用户长期日记资产，提升留存
- 对后续迭代：完整闭环跑通后，可在此基础上扩展情绪分析、回顾提醒、多风格日记等能力

## 3. 术语与角色定义

- **情绪日记（Emotion Diary）**：本产品名称，指围绕照片讲述与情绪记录展开的日记类应用。
- **Agent**：本产品中的 AI 智能体，承担识图、情感陪伴对话、日记生成三项职责。
- **识图对话**：用户上传照片后，Agent 识别图片内容并围绕照片背景与用户进行的对话。
- **日记生成阶段对话**：用户在生成日记前与 Agent 围绕照片展开的完整对话。
- **二次对话**：日记保存后，用户在日记详情页内新开启的、与 Agent 的对话。
- **生成阶段对话摘要**：将日记生成阶段的对话内容压缩后，作为上下文注入二次对话。
- **用户角色**：注册用户（唯一角色，可管理自己的照片与日记）；本首版不设管理员角色。

## 4. 适用范围

- 形态：Web 网页应用，浏览器访问，桌面端优先、兼容移动端浏览器。
- 用户：面向有记录习惯、希望被陪伴的泛大众情绪记录者。
- 场景：用户手头有一张有故事的照片（旅行、聚会、日常瞬间等），希望记录并倾诉当下感受。
- 功能边界：覆盖上传照片、AI 识图、情感陪伴对话、生成日记、保存与查阅、二次对话的完整闭环，以及支撑闭环的注册登录与数据存储。
- 技术边界：前端采用 React，后端采用 FastAPI，大模型应用开发框架采用 LangGraph；图片存 MinIO，用户/日记/对话等数据存 MySQL，均通过 Docker 部署。

## 5. 非目标（不在本版本范围）

- 不做日记分享、导出（图片/PDF）与社交互动，日记仅用户自己可见。
- 不做纯本地存储方案，首版采用服务端存储（MinIO + MySQL）。
- 不做多风格日记选择，首版为单版本生成、支持重新生成。
- 不做情绪趋势分析、数据统计报表、日历回顾等分析类功能。
- 不做第三方登录（微信/QQ 等），首版仅邮箱方式登录。
- 不做多端实时同步、离线编辑、协同编辑等能力。

## 6. 功能需求

- **FR-1 注册登录**：系统须支持用户注册与登录，登录方式支持"邮箱 + 验证码"与"邮箱 + 密码"两种；注册时通过邮箱验证码校验邮箱有效性；未登录用户访问核心功能时须被引导登录；登录态失效须提示重新登录；用户数据须按用户维度隔离。
- **FR-2 照片上传**：登录用户须能上传照片（本地选择文件、移动端可调用相机），系统须对文件类型、大小做常规校验（如单张大小上限、常见图片格式），校验通过后上传至 MinIO 并返回可访问的图片地址。
- **FR-3 照片识别与解析**：系统须调用第三方多模态大模型 API（模型选型暂不限定，开发阶段确定），对上传的照片进行内容识别与解析，提取画面主体、场景、氛围等要素，作为后续对话与日记生成的输入。
- **FR-4 情感陪伴对话**：识别完成后，Agent 须围绕照片内容与用户展开对话，以情感陪伴为主，语气温和、以倾听和共情为主；对话须支持多轮，并逐轮保存。
- **FR-5 日记生成**：用户须能触发"生成日记"；系统须基于照片识别结果与生成阶段对话，调用大模型生成一篇笔法柔和的日记；须明确日记的目标字数区间，并制定"柔和笔法"的提示词（Prompt）规范以约束输出基调；日记为单版本，用户可对同一素材重新生成以覆盖上一版本。
- **FR-6 日记保存**：生成的日记须与对应的照片、生成阶段对话一并保存到 MySQL；保存时须记录创建时间、用户归属等信息。
- **FR-7 日记查阅**：用户须能查看日记列表并按时间浏览，进入详情页可查看日记正文、对应照片及生成阶段对话记录。
- **FR-8 二次对话**：在日记详情页，用户须能与 Agent 新开一轮对话；该对话为独立会话，但须将生成阶段对话的摘要（通过调用大模型对生成阶段对话进行压缩生成）作为上下文注入，使 Agent 了解日记来龙去脉。
- **FR-9 数据存储与部署**：系统须通过 Docker 部署 MinIO 与 MySQL；图片存入 MinIO，其余结构化数据（用户、日记、对话、摘要等）存入 MySQL。
- **FR-10 数据可见性**：日记及照片仅对所属用户可见，任何跨用户的越权访问须被拒绝。

## 7. 关键流程 / 交互说明

**核心主流程（上传 → 生成 → 保存）：**
1. 用户登录（邮箱 + 验证码 / 邮箱 + 密码）后进入首页 / 记录页
2. 用户上传一张照片，系统校验并上传至 MinIO
3. 系统调用多模态大模型识别照片，返回画面解析结果
4. Agent 基于识别结果发起对话，用户与 Agent 就照片背后的故事交流（可多轮）
5. 用户点击"生成日记"，系统结合识别结果与对话上下文生成柔和笔法的日记
6. 用户确认后保存，系统将照片、日记、生成阶段对话写入数据库
7. 若用户不满意，可点击"重新生成"，覆盖当前日记版本

**查阅与二次对话流程：**
1. 用户进入日记列表，按时间浏览历史日记
2. 进入某篇日记详情页，查看日记正文、照片与生成阶段对话
3. 用户点击"继续聊聊"，系统在详情页内新开会话
4. 系统将生成阶段对话的摘要作为上下文注入，用户与 Agent 展开新一轮对话
5. 新对话内容按日记维度保存，供下次继续

**异常与边界流程：**
- 照片识别失败 / 大模型超时：提示用户"识别失败，请重试"，允许重新识别或更换照片
- 日记生成失败：保留已有素材与对话，允许用户重新触发生成
- 图片超出大小 / 格式限制：前端即时提示并阻止上传
- 登录态失效：跳转登录页并提示重新登录

## 8. 风险与依赖

**风险：**
- 第三方多模态大模型 API 的稳定性与响应时延直接影响核心体验，需设计超时与重试机制
- 大模型输出内容不可控，日记与对话可能出现不符合"柔和"基调或不当表述，需评估内容安全与兜底策略
- 用户上传照片涉及个人隐私，服务端存储（MinIO + MySQL）需重视数据安全与访问控制
- 图片存储于 MinIO，需考虑容量增长、清理策略与访问地址有效期

**依赖：**
- 前端 React、后端 FastAPI 技术栈
- 大模型应用开发框架：LangGraph
- 第三方多模态大模型 API（识图 + 语言生成，模型选型暂不限定）
- 邮箱服务（用于发送注册/登录验证码）
- Docker 环境及 MinIO、MySQL 的镜像与部署资源

## 9. 验收标准

- [ ] 用户可通过"邮箱 + 验证码"或"邮箱 + 密码"完成注册与登录，未登录无法访问日记核心功能
- [ ] 用户可上传符合要求的照片，非法格式或超限文件被拦截并给出提示
- [ ] 上传的照片成功存入 MinIO，并可通过返回地址正常访问
- [ ] 系统能调用多模态大模型识别照片内容，返回可用的解析结果
- [ ] 用户可与 Agent 围绕照片进行多轮情感陪伴对话，对话可持久化
- [ ] 用户可基于照片与对话生成一篇笔法柔和的日记，且为单版本
- [ ] 日记生成已按明确的字数区间与"柔和笔法"提示词规范执行
- [ ] 用户可对同一素材"重新生成"日记并覆盖上一版本
- [ ] 生成的日记连同照片、生成阶段对话成功保存至 MySQL
- [ ] 用户可在列表中查阅历史日记，详情页可见日记正文、照片与生成阶段对话
- [ ] 用户可在日记详情页新开与 Agent 的对话，且生成阶段对话摘要已通过模型压缩并注入上下文
- [ ] 用户仅能访问自己的照片与日记，越权访问被拒绝
- [ ] MinIO 与 MySQL 通过 Docker 正常部署运行

## 10. 待确认问题（Open Questions）

以下问题已经确认，作为开发依据：

- 技术栈：前端 React，后端 FastAPI。
- 大模型开发框架：LangGraph。
- 大模型选型：暂不限定，开发阶段确定。
- 登录方式：邮箱 + 验证码，或邮箱 + 密码。
- 照片限制：采用常规限制（具体阈值开发时按常规设定）。
- 对话摘要：通过调用大模型压缩生成。
- 日记字数与"柔和笔法"提示词规范：需要，开发时须明确制定。
- 并发量级：不作考虑。

仍需在开发阶段确认的问题：

- MinIO 图片访问方式（公开 URL / 预签名 URL）及有效期策略：当前存疑，开发时必须向开发者确认。
- 日记目标字数区间与"柔和笔法"提示词的最终文案：需在开发阶段落地为具体规范。
- 照片"常规限制"的具体阈值（单张大小上限、支持格式、单次/单日数量）：需在开发阶段量化。
- 邮箱验证码的发送服务（SMTP / 第三方邮件服务）及其配置：需在开发阶段确定。
